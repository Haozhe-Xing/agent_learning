# 15.7 总结：按任务与验证证据选择实现

本节收束第三部分的选择过程。先回到已有助手，说明一个具体问题，再用固定输入比较候选实现。继续使用最小实现、采用一个开发库，或只借鉴一个案例中的机制，都可以形成完整结论。

## 用六章回答不同问题

| 问题 | 实现层次 | 候选章节 | 固定任务的检查点 | 不选或停止条件 |
|---|---|---|---|---|
| 适配代码重复且难以维护 | 开发库 | [第10章 LangChain](../chapter_langchain/README.md) | 同样的输入与工具权限下，结果、错误和调用记录是否一致？ | 没有减少维护负担，或破坏旧验收用例 |
| 暂停、恢复、确认与分支难以追踪 | 开发库 | [第11章 LangGraph](../chapter_langgraph/README.md) | 同一失败点重跑后，是否正确恢复且不重复有副作用的动作？ | 现有简单流程已经满足这些要求 |
| 需要从聊天入口使用助理 | 产品案例 | [第12章 OpenClaw](../chapter_openclaw/README.md) | 一个指定渠道中的身份、会话和工具权限是否符合任务边界？ | 接入条件不满足，或只需要后端能力 |
| 需要理解跨会话记忆与技能积累 | 产品／架构案例 | [第13章 Hermes](../chapter_hermes/README.md) | 固定未用于编写技能的任务，比较结果，并验证停用、审查和回退 | 没有长期需求，或缺少独立改进判据 |
| 需要编程助理或代码操作案例 | 产品／架构案例 | [第14章 Claude Code](../chapter_claude_code/README.md) | 固定代码任务的补丁、真实测试、授权和失败记录 | 任务不涉及编程，或无法复现运行条件 |
| 需要研究组件替换与插件管理 | 架构案例 | [第15章 DeepSeek Harness](./README.md) | 固定版本下替换一个组件，检查接口、状态与失败清理 | 没有替换需求，或验证成本超过收益 |

这是按问题分流的学习表。LangChain 与 LangGraph 可以组合，但无需把两者视为必修连续栈；第12–15章则按场景选择，不要求逐个安装。产品案例提供观察对象，架构案例提供设计问题，两者都不能自动推出部署结论。

## 做一次能够复查的对照

从[贯穿项目](../learning_project.md)保留一份离线基线：

```bash
python -m reference_code.evidence_assistant
```

主应用从虚构项目文档回答多个问题，分别记录检索证据、计划状态、上下文预算和带引用的报告。默认按原文摘录，不调用真实模型或在线搜索。保留输入文档与问题，用同一份资料和验收要求比较候选实现。

对候选实现复用输入、预期、工具权限与预算，只改变要研究的那一层。至少保留以下对照：

| 固定输入或故障 | 应观察到的行为 |
|---|---|
| 默认项目文档与三个问题 | 各题答案有原文和来源，计划状态与验收结果分开保存 |
| 修改一份文档中的回退要求 | 回答随原文变化，不继续使用旧资料 |
| 一个问题没有匹配证据 | 该题保留 `no_evidence` 等失败原因，整体未完成且不能验收通过 |
| 必需证据超出上下文字节预算 | 显式失败，不能静默丢弃证据后报告成功 |
| 未授权工具或预算耗尽 | 记录停止原因，不产生被禁止的动作 |
| 任务要求恢复或人工确认 | 在预先指定的位置中断，核对恢复、确认和重复动作情况 |

最后一项只有在本次选择涉及这些机制时才加入。调研应用没有提供持久恢复或人工确认；必须为候选实现补相应实验。若只想比较单位处理与数值契约，可另选 `python -m reference_code.evidence_assistant.demo --all` 的基础计算练习；不要把两项不同任务的成功直接当成同题对照。

开发库的现有配套入口为 `examples/chapter12/customer_service.py` 与 `examples/chapter13/content_workflow.py`，目录保留历史编号。它们使用不同任务，默认固定模型输出，分别演示工具编排与状态图；不能把这两个示例的成功直接当成同题选型结果。第12–15章也没有配套的四产品统一离线适配器。没有实际运行的候选应写“未运行”，无法保持同一条件的实验应写“不可直接比较”。

## 把选择理由写成记录

| 字段 | 应填写的内容 |
|---|---|
| 要解决的问题 | 现有助手出现了什么可复现的维护或执行问题？ |
| 基线与候选 | 原实现与待替换的接口、状态机制或产品；精确版本与配置 |
| 固定条件 | 输入、预期结果、模型模式、工具权限、预算与失败用例 |
| 实际证据 | 测试结果、调用轨迹、来源、恢复记录、耗时及调用量；未运行项另记 |
| 采用的改变 | 哪一层被替换，业务逻辑与验收标准怎样保持？ |
| 结论与停止条件 | 采用、保留原实现或继续验证；触发回退的具体条件 |

模型效果需要单独的代表性任务集。一次演示通过、某个产品的功能介绍或一种插件接口，都不足以证明整体正确性与安全边界。读架构时，应把公开可观察行为、版本相关实现和自己的推断分开记录。

## 按下一个问题继续

如果单 Agent 已满足需求，可以直接整理回归、权限与部署要求。只有出现可独立分工的任务，才通过[第16章 多 Agent 协作](../chapter_18_multi_agent/README.md)与单 Agent 对照；任务跨进程或服务边界时，再按需学习[第17章 通信协议](../chapter_19_protocol/README.md)。角色数量与协议需求分别判断。

随后在[第18章 评估](../chapter_20_evaluation/README.md)、[第19章 安全](../chapter_21_security/README.md)和[第20章 部署](../chapter_22_deployment/README.md)中完善已有证据与约束，再选择第21–23章的[编程助手](../chapter_23_coding_agent/README.md)、[数据分析](../chapter_24_data_agent/README.md)或[多模态](../chapter_25_multimodal/README.md)项目。第24–25章的研究进阶内容安排在综合项目之后，应用路线可以按研究目标再选读。

本部分的完成证据是一份可复查的选择记录：当前问题、采用的实现、通过与失败的用例，以及何时停止或回退。
